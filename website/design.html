A design team you can install.

analyzthis_design is a free npm package. It puts named specialists inside Cursor, Claude, or a similar AI coding tool. They wireframe, critique, argue, and gate the work — so you get a verdict, not a polite paragraph.

Who this is for

Built for people who already have an AI coding tool.

Designers who are understaffed. Developers and PMs who need to design. If you can open Cursor or Claude, you can run this team. You do not need a new app.

What you can do

Eight jobs. One installed team.

Pick the job. Type the command in your AI chat. The team does the rest and stops at a human decision.

Wireframe a new screen

When the screen does not exist yet. The team writes two competing text wireframes: a quiet, minimal one and a dense, power-user one. They argue. You pick a direction before anyone opens Figma or writes code.

New work/ux-ideator/noor/anuj
  1. You describe the user, the job, and the stack.
  2. The team maps the task so the wireframe is not decoration.
  3. Noor drafts the simple path. Anuj drafts the expert path.
  4. Arjun, Meera, Zara, and Priya pressure-test both.
  5. You get two full text wireframes plus a synthesis — not a single “nice” mock.

Use /noor alone for a fast minimal sketch. Use /anuj alone when the user is an expert who needs density on day one.

In Cursor or ClaudeChat
/ux-ideator Design a settings page for a B2B dashboard.
Primary user: ops manager, daily use.
Stack: Next.js + shadcn.
Produce full text wireframes for Concept A and Concept B.

Design, spec, then build

When you need more than a sketch. The producer path turns ideation into a DesignSpec — layout, tokens, components, and states — then waits for gates to pass before anyone implements.

Handoff/design-director/design-spec
  1. Ideation produces two concepts, same as above.
  2. A DesignSpec is written: what goes where, which tokens, which components, which empty/error/loading states.
  3. Hard gates check design-system fit and information hierarchy.
  4. If a gate fails, you get a blocker and a fix — not a pretty wrong file.
  5. Implementation starts only when you approve build mode.

This is the path for a senior-designer handoff. The team prepares. You still sign.

Producer pathChat
/design-director Design a notifications settings page.
Use our shadcn components and tokens
from the knowledge bank.
Produce a DesignSpec. Implement only
after spec gates pass.

Critique an existing design

When the screen already exists — in code, in Figma, or as a screenshot. The team does not compliment it. They score it, object, and return SHIP, REVISE, or BLOCK with the top three fixes.

Review/persona-orchestrator/design-critic
  1. Say what the user is trying to finish. Paste a URL, a file, or a frame.
  2. A router picks the smallest useful set of specialists. Default is not “everyone.”
  3. Ask for full when you want the complete chain.
  4. Specialists raise objections with evidence. Agreement is earned.
  5. You get a composite score, a hierarchy check, a verdict, and ranked fixes.

Do not use these commands when you want a wireframe. They review. They do not invent a new screen.

Assess onlyChat
/persona-orchestrator Critique this login page
for UX friction and hierarchy.
Assess only — do not implement.

/design-critic Full review of the invoice screen.
Run all personas in full mode.

Review against a PRD or user story

When “does this look good?” is the wrong question. The story gate asks whether a real person can finish a real job, using your PRDs, Figma, and design system as ground — not vibes.

Task-first/ux-story-gate
  1. The team looks for PRDs, stories, and design-system files in the project.
  2. It builds a task map: trigger, steps, decision, done.
  3. It routes only the specialists that job needs.
  4. Optional browser check confirms the live screen matches the claim.
  5. Assess-only mode keeps implementation off until you ask.

Set visual direction

When the team is arguing about “feel” with no shared board. A mood board collects web references and your design-system patterns, tags them, and runs the same specialists over the references — not over a blank prompt.

Direction/mood-board
  1. You name the product type and the mood you want (trust, density, calm).
  2. The team gathers references and patterns from the design-reference library.
  3. You can add your own URLs and notes, then rerun.
  4. Arjun, Meera, Priya, Zara, and Noor score the board.
  5. A board file is written into the project so you can inspect every pick.
Mood boardChat or CLI
/mood-board Build a mood board for a
B2B fintech dashboard.
Trustworthy, high-contrast, data-dense.
Include 3 web references.

npx analyzthis_design moodboard create \
  --task "B2B fintech dashboard" --auto

Index the project before opinions

Kavi is not a critic. Kavi is the archivist. Run this once per repo so every later command reads your brand, PRDs, components, and past decisions — instead of inventing a generic app.

Grounding/kavicollect
  1. Kavi scans the repo: pages, tokens, components, research, stack.
  2. It writes an Obsidian-compatible vault on your machine.
  3. Optional: an LLM enriches the notes. Without keys, the draft vault still lands.
  4. A knowledge bank is synced into your IDE. Personas read it first.
  5. You can also connect an existing vault and sync that instead.

If you skip Kavi, the team still runs — it just guesses more. Ground first.

Once per projectTerminal
npx analyzthis_design collect

npx analyzthis_design connect \
  --vault ~/Documents/MyVault
npx analyzthis_design sync --target all

Run the team without paying for extra keys

The CLI can drive the same graph from the terminal. Default v2.0 mode plans on a strong model, then runs small chunks on cheap or free models — including local Ollama. If you set no keys at all, Devi asks your host IDE to voice each specialist.

CLIrun/devi
  1. Start a run with a task in plain language.
  2. A planner breaks the work into chunks. The planner stays strong on purpose.
  3. Chunks go to local, free, or cheap models. Results merge into one verdict.
  4. In host mode, pending prompts wait. Type /devi in Cursor or Claude. Continue the run.
  5. Telemetry remembers which models actually worked for each chunk type.
v2.0 defaultTerminal
npx analyzthis_design run \
  --task "Review invoice approval screen"

npx analyzthis_design run \
  --task "Review invoice screen" --budget free

npx analyzthis_design run-unchunked \
  --task "Review invoice screen" --provider host
# then in Cursor: /devi
npx analyzthis_design run-unchunked --continue \
  --task "Review invoice screen" --full

Let the team learn — with your approval

After work ships, you can tell the system what landed. It harvests lessons and may propose prompt, reference, or routing patches. Nothing becomes canonical until you review it. Silent self-rewrite is not allowed.

Learningevolveoutcome
  1. Mark whether a persona’s output actually shipped.
  2. Extract lessons from accepted work and confirmed outcomes.
  3. The system proposes patches. You see the diff.
  4. You accept or reject. The team does not evolve in the dark.
Human-reviewedTerminal
npx analyzthis_design outcome --confirm
npx analyzthis_design evolve --extract
The roster

One job each. No “do everything.”

Eight specialists, each with one job. For a full screen, use the orchestrator so they speak in order and Raj only appears when they deadlock. Devi — below — is not a ninth critic; she is the host that voices them when you have no extra API keys.

KV
/kavi

Kavi

Knowledge archivist. Scans the repo, builds a vault, fills the knowledge bank. Speaks before opinions form. Not a critic.

AR
/arjun

Arjun

UX and visual design. Hierarchy, color, type, spacing, components, accessibility, style fit, and the one interaction that is doing too much work.

ME
/meera

Meera

Business. Retention, adoption risk, whether the hierarchy matches the north-star metric. Will kill a pretty screen that does not move the number.

PR
/priya

Priya

Feasibility. T-shirt effort, state-machine traps, what will slip the sprint. Protects you from a design that cannot be built this quarter.

ZA
/zara

Zara

Delight. Exactly one peak moment. Will not “fix contrast” and call it joy. Contrast goes back to Arjun and the design-system gate.

NO
/noor

Noor

Minimalist IA. Progressive disclosure, one primary action, a ranked information hierarchy that is declared out loud.

AN
/anuj

Anuj

Power-user advocate. Density, bulk actions, keyboard shortcuts. Will not hide expert tools behind a wizard “for simplicity.”

RJ
/raj

Raj

Arbitrator. Never speaks first. Resolves a stalemate with five ranked product principles after everyone else, including Zara, has gone.

DV
/devi

Devi — the voice of the LLM you’re already using

Not a ninth critic. Devi is the host runtime. When you have no extra API keys, the other eight personas write their prompts to a queue and Devi voices each response from the model in your Cursor, Claude, or Codex — the same model you are already chatting with. The team still runs; you just provide the voice.

How a critique run works

Gates, not vibes.

A full critique is a graph, not a chat. The same graph runs from your IDE or from the CLI.

01
Intake

You name the task

A Figma URL, a file, a screenshot, or a sentence. The story gate looks for PRDs and the design system before anyone opines.

02
Route

The smallest useful team

A mixture-of-experts router picks who speaks. Full chain only when you ask. Extra agents cost coordination, so they must earn a seat.

03
Deliberate

Disagreement is required

Specialists object in parallel, cite evidence, and cannot repeat themselves on a re-run. Low satisfaction is the default.

04
Delight last

Zara, then Raj if needed

Delight is one peak, not a polish pass. Raj never opens. He only closes a structural deadlock.

05
Gate

SHIP / REVISE / BLOCK

Design-system, hierarchy, and verify gates do not downgrade. A failed standard is a blocker with a correction, not a suggestion in a footnote.

Where it runs

Same team. Different hosts.

Install once per machine. Skills are plain SKILL.md files. The CLI is the same everywhere. Only the invoke prefix changes.

Cursor

Skills in ~/.cursor/skills. Type /getting-started.

Claude Code

Skills in ~/.claude/skills. Same slash commands.

Codex CLI

Skills in ~/.codex/skills. Reference them from AGENTS.md.

Grok Build

Skills in ~/.grok/skills. Slash commands.

Windsurf

Skills in the Windsurf folder. Invoke with @, not /.

CLI

npx analyzthis_design run — host-agnostic, with or without keys.

Trust

Open source on purpose.

MIT license

Use it, fork it, read every file. The published package is plain source — no obfuscation, no minified surprise.

Consent-based install

npm install does not write into your AI folders. Skills land only when you run npx analyzthis_design --target.

You still sign

Assess-only modes and hard gates keep implementation off until you approve. The team prepares. You decide.

No required API bill

Host mode uses the model you already pay for in Cursor or Claude. Local Ollama and free endpoints are first-class.

Install

Three commands. Then /getting-started.

Node.js 16 or newer. An AI coding tool. That is the whole requirement.

One-time setupTerminal
# 1. Install the package
npm install -g analyzthis_design

# 2. Copy skills into your AI tool (you choose the target)
npx analyzthis_design --target cursor
npx analyzthis_design --target claude
npx analyzthis_design --target all

# 3. In the project, ground the team once
npx analyzthis_design collect

# 4. In chat
/getting-started

After a package update, reinstall skills with npx analyzthis_design --target all --force. Reprint help anytime with npx analyzthis_design welcome.
